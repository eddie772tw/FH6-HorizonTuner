## 2. 程式現況與可重現問題

正式 owner 是 [chassis.rs](../../backend-rust/src/tuning/chassis.rs)，由 [mechanical](../../backend-rust/src/tuning/calculation.rs) 與 [workflow](../../backend-rust/src/tuning/workflow.rs) 共用；舊 CLI `solve chassis` 不是此次驗收入口。

### 2.1 虛擬空力確實進入 Road 彈簧

`resolve_aero_downforce` 的行為：兩軸皆空白／零值時推導總車重 20%；僅一軸正值時，依配重與 drivetrain modifier 推導另一軸。Road 再加入前 `aero.front / 20`、後 `aero.rear / 50` 的彈簧增量。

`TuningCarParams` 沒有 `adjustability`，因此底盤公式本身不知道 `Fixed`、`Front Only`、`Rear Only`。這些能力存在於 raw profile 與 [capabilities.rs](../../backend-rust/src/tuning/capabilities.rs)，但目前不能阻止空力被推導後間接改變彈簧。

正式 CLI 重播證實：Impreza 測試參數加上 `adjustability.aero = Fixed`、兩軸下壓力為零，Road 仍輸出前 **15.5**／後 **12.3 kgf/mm**。把能力改成 `Rear Only` 並只填後 100 kgf，前彈簧仍為 **15.5**，後為 **11.7**；僅修正「兩軸皆零」不足以涵蓋單軸套件。

這些 capability 組合是本輪控制案例，不表示已確認該 Subaru 在遊戲中的實際改裝狀態。沒有可調套件亦不表示車輛真實空力為零；應描述為「沒有可用下壓力輸入，計算不加入推測增量」。

### 2.2 FWD 已有獨立策略

現行 Road FWD 使用前 `max(0.10, wf - 0.10)`、後 `min(0.90, wr + 0.10)`，並依彈簧比修正阻尼。其 [原始設計紀錄](../archive/tuning/road-meta-iteration-20260913.md) 明確將這些係數標成有界工程起點。

原計畫 R1 沒有說明是替換還是疊加：替換會反轉既有 FWD 策略；直接疊加 +10% 可能抵消原本 −10%，不能宣稱只新增煞車支撐。推薦 R3 修正版保留該分支，但仍須驗證空力移除後 FWD 阻尼的連帶數值變化。

### 2.3 UI 的零值代表 Auto

[Step1GoalSetup.tsx](../../frontend/src/features/tuning/components/Step1GoalSetup.tsx) 將 `<= 0` 判定為 Auto、停用數值輸入；取消 Auto 時直接填 50 kgf。[profile_defaults.json](../../backend-rust/src/tuning/profile_defaults.json) 又預設 aero 為 Adjustable，兩軸值為零。

因此不能只改 Rust 算式並保留「Auto」文字。新契約需要明確區分未提供資料、不可調以及明確設定值；不可把預設 50 kgf 當成玩家輸入證據，也不可把缺少能力欄位直接當成已安裝套件。

### 2.4 四捨五入仍有未涵蓋反例

`clamp_round` 在範圍內沒有任何一位小數可表示時，退回 `r1(min/max)`，可能再次越界。正式 CLI 重播：

| 前彈簧區間 | 輸出 | 預覽結果 |
| --- | --- | --- |
| `[3.11, 3.11]` | `3.1`，低於下限 | `unavailable / value-outside-range` |
| `[3.11, 3.14]` | `3.1`，低於下限 | `unavailable / value-outside-range` |

這是合成邊界反例，尚未宣稱遊戲出現這種滑桿區間。數學上此時無法同時滿足「限制在原範圍」及「一定一位小數」：優先保留合法精度，將顯示四捨五入與實際可套用值分清；若有可靠遊戲刻度資料則依刻度處理。不能用放寬容差掩蓋問題。現有 bounds test 只覆蓋較寬區間，沒有抓到這些案例。

### 2.5 使用者追加：下壓力可選與單軸空力平衡反推

此項為使用者已指定的開發需求，取代初版「另一軸一律不推導」的建議。正式解析由 Rust 統一完成，桌面、Companion、mechanical 與 workflow CLI／MCP 共用；不影響 Road 基礎模型仍待選定的狀態。

| 玩家輸入 | 空力平衡要求 | 底盤計算行為 |
| --- | --- | --- |
| 前、後皆未填 | 不要求；即使另有平衡值也不能憑空生成總下壓力 | 不進行任何下壓力補正，維持基礎底盤結果 |
| 只填前下壓力 | 必須明確填入空力平衡 | 反推後下壓力後，以完整前後值進行補正 |
| 只填後下壓力 | 必須明確填入空力平衡 | 反推前下壓力後，以完整前後值進行補正 |
| 前、後皆已填 | 不要求 | 直接以兩個輸入值進行彈簧硬度及其他已有空力計算項目的補正 |
| 單軸已填，但平衡未填、無效或無法求解 | 顯示需要補齊／修正平衡 | 不產生可套用的完整空力補正建議；可保留並明確標示未補正的基線預覽，不默默當作未填兩軸 |

**空力平衡的定義**：前軸占總下壓力的比例，與前軸車重分佈不同。UI 顯示「前軸空力占比 (%)」，例如 40% 代表前／後 40:60；內部以 `b = 百分比 / 100` 表示。沿用 `aeroBalance` 欄位時，必須明確鎖定這個定義。

```text
b = Ffront / (Ffront + Frear)
只填前：Frear  = Ffront × (1 - b) / b
只填後：Ffront = Frear  × b / (1 - b)
```

例：只填前 100 kgf、前軸空力占比 40%，反推後為 150 kgf；只填後 150 kgf、占比 40%，反推前為 100 kgf。兩者與直接填前 100／後 150 的底盤補正結果應一致。

開發契約與邊界：

- **真正可選與明確來源**：新模型使用空白／missing／null 表示未填，保留玩家明確輸入的有限非負值；明確填入的 0 與未填分開。舊模型的 0 曾代表 Auto，舊草稿需依版本／輸入來源處理，不可直接當成已確認的零下壓力。
- **不得套用隱藏預設**：目前 `profile_defaults.json` 有 `aeroBalance: 0.5`，但正式 `TuningCarParams` 與 chassis 尚未讀取此欄位。新模型不得把 loader 補出的 0.5 視為玩家已填平衡；預設應保留未填語意，舊值缺少明確輸入來源時須讓玩家確認。沿用 Rust 型別、草稿型別與儲存快照時要一起處理，不能只補 UI。
- **單軸要求只在必要時出現**：前後下壓力為兩個可留空欄位；恰好填一軸時顯示平衡必填及缺值提示。空力平衡改變時重算推導軸，推導值標示「由空力平衡計算」，不回寫成玩家輸入，避免被誤判成雙軸已填。
- **雙軸輸入優先**：兩軸都有值時，不用留存的平衡覆蓋任一軸。總量大於 0 時可顯示由兩值算出的實際平衡；兩者皆為 0 時不補正，平衡顯示不適用，避免 0/0。
- **可解性與有限值**：通常反推使用 `0 < b < 1`。端點只有在結果唯一可解時成立：前已知且 `b=1` 可得後 0，後已知且 `b=0` 可得前 0；前已知且 `b=0`、後已知且 `b=1` 均不做除零推導，要求補填另一軸或修正平衡。負值、非有限值、超出 0–100% 或溢出的結果須明確拒絕，不偷偷 clamp 成另一個平衡。保留計算精度，最後再按輸出規則處理。
- **能力與負載分開**：Fixed／Front Only／Rear Only 限制遊戲可調控制，不等於該軸沒有空力負載；依本需求解析完成的前後下壓力可供底盤補正使用，但不會因此解鎖原本不可調的空力設定。不得再用車重分佈、驅動方式或車重 20% 代替玩家要求的空力平衡。
- **共用補正輸入**：下壓力解析結果及來源供所有依賴空力的底盤公式共用。現行正式實作直接影響 Road 彈簧，並經彈簧比影響 FWD 阻尼；其他底盤項目若已有／後續選定空力模型，沿用同一解析結果。此次輸入需求本身不作為新增未校準 ARB、車高、差速器補正係數的依據。

新增驗收：上述五類狀態、前／後反推與雙軸直接輸入的一致性、改變平衡後推導值更新、刪除一軸後重新要求平衡、雙軸皆空時平衡值不能啟動補正、舊預設 0.5 不算明確輸入、雙軸值不受殘留平衡影響、明確零值／端點／非有限值與單位往返。這是待實作的驗收規格，尚未宣稱產品已支援。

## 4. 分別評估 Road 三條路徑

### R1：固定偏置不能直接等同動態載荷儲備

由準靜態力矩平衡可得縱向轉移量 `ΔFz = m × |ax| × hCG / L`，佔總重量比例為 `(|ax|/g) × hCG/L`。僅用 AWD/FWD/RWD 無法決定減速度、重心高度、軸距及多少載荷經彈簧承擔。前後 anti-dive／anti-lift 與俯仰幾何亦有耦合，參考 [OptimumG：The anti-antis](https://optimumg.com/the-anti-antis/)。

若要估算觸底風險，還需要可用壓縮行程、運動比、緩衝塊與動態觀測。車高不是可用避震行程。原模型既沒有這些輸入，也沒有載荷／行程約束，因此目前只是改變滑桿位置。

此外：

- R1 同時增加前軸比例與減少後軸比例，不保證增加整車支撐。若前後滑桿跨度相同，總剛性和完全不變；跨度不相同時，總量依跨度差改變。
- 它仍沿用獨立滑桿插值，不能解決原文件在 Rally 指出的同類截距／跨度不對稱現象。
- `min(0.85, wf + Δ)` 在 `wf > 0.85` 時會把前比例降到原始配重以下；不符合「增加前儲備」語意。應有後置引擎、極端配重與邊界案例。
- 不能由前彈簧較硬直接推出更少推頭或更快圈速；這需要輪胎、ARB、阻尼及實際操控資料共同判讀。

**採用條件**：把係數標成實驗先驗；明確處理 FWD；先用固定設定與相同情境比較前避震行程、制動與轉向反應，再決定是否有必要保留此偏置。

### R2：公式方向合理，但資料與解讀不足

簡化單輪簧載模型應寫成：

```text
kwheel [N/m] = (2πf)² × msprung_corner [kg]
kspring [kgf/mm] = kwheel / (r² × 9806.65)
r = 彈簧位移 / 輪心位移
```

若採相反定義 `MR = 輪心位移 / 彈簧位移`，則乘 `MR²`。原式除數 `9806.65` 的單位換算正確，但隱含運動比為 1；也必須說明質量是每輪簧載質量，不能直接套整軸重量。[OptimumG Part Two](https://optimumg.com/wp-content/uploads/2020/01/SpringsDampers_Tech_Tip_2.pdf) 提供運動比與 SI 單位推導。

原文 7.8／6.6 若假設運動比為 1，反推每輪簧載質量約 **400.32／309.92 kg**。原文件未提供這兩項資料，故不能獨立確認此結果。作為敏感度示例，若錯把全部重量都當簧載質量，會算出 8.3／7.1；若再任意取 95% 為簧載重量，則為 7.9／6.8。這些只是展示假設對結果的影響，不是推薦的簧載比例。

目前正式 `TuningCarParams` 沒有簧下質量、運動比或每軸目標頻率。其他實驗／預設資料內有 `target_ride_frequency`，不代表正式 chassis 已具備計算 R2 的資料契約。

原計畫另有兩點需要修正：

- 不能把 2.2/2.3 Hz 一概稱作原廠舒適取向。OptimumG 的粗略參考為乘用車 0.5–1.5 Hz、房車賽車 1.5–2.0 Hz；該範圍不是 FH6 校準資料。
- 後頻率略高可能改善某些路面輸入下的俯仰，但 flat ride 取決於速度、軸距及阻尼；2.3/2.2 僅高約 4.5%，不能單憑這一對數字宣稱達成 flat ride。參考 [OptimumG Part One](https://optimumg.com/wp-content/uploads/2020/01/SpringsDampers_Tech_Tip_1.pdf)。

ARB 主要對左右差動位移提供支撐；理想對稱純升沉／俯仰中，同軸左右同向運動不會扭轉 ARB。因此「彈簧偏軟，補粗 ARB 即可」不能代替煞車或落地防觸底驗證。

**採用條件**：取得有來源的必要資料，或建立可辨識且有品質門檻的量測流程。無資料時回報 unavailable，不要求玩家猜測隱藏參數，也不默認運動比為 1 後宣稱精確物理解。

### R3：適合作為可歸因的第一階段修正

R3 保留目前滑桿與配重的映射，兩軸皆未填時取消空力增量。對此 Subaru 能直接解除由虛擬下壓力導致的觸頂，同時便於比較修正前後。

建議版本要保留 FWD 專屬偏置，並依 2.5 的使用者需求解析可選下壓力：單軸已填且有明確空力平衡時可反推另一軸；雙軸已填時直接採用。為了最小化同時改動，可暫時保留既有空力增量係數，但須標明仍是待校準的經驗模型，不能當成已知速度下的真實輪上負載。

**限制**：R3 不會保證任何車都不碰上下限，也不會證明前後頻率或操控最佳。相同配重與相同滑桿範圍下，無空力基線不隨總重量改變；這是滑桿啟發式與 R2 的本質差異。它適合先修已證實錯誤，再收集單一變因證據。

## 5. Rally A 的適用邊界與修正

以配重分配彈簧有工程上的合理起點，但只有在前後運動比相近、簧載質量比例可用等假設下，才接近相同輪上頻率。前後彈簧數字誰大誰小，不能單獨判定車輛失衡；`Kf + Kr` 也應稱為此算法的剛性總量指標，不能直接當整車輪上剛性。

令 `w = wf/100`、目標總量為 `T`。若要維持精確比例且同時滿足兩軸限制，必須存在：

```text
T_low  = max(KminF / w, KminR / (1-w))
T_high = min(KmaxF / w, KmaxR / (1-w))
T_low <= T <= T_high
```

原 A 的各軸獨立 clamp 沒有維持此條件。例如合成輸入前重 70%、前 `[3,10]`、後 `[8,12]`、ratio=0.35，T=14.85，原始目標為 10.395／4.455，截斷後成為 **10／8**；剛性比 1.25，配重比 2.333。此範圍內不存在符合配重的剛性比，不能用測試強制保證。

建議先採「上下限優先，未截斷時驗證配重分配，截斷時記錄比例偏離」的透明啟發式。若改為先將 T 限制在可行區間，會改變賽事目標總量，是另一個候選策略，需要另行比較；`T_low > T_high` 時也仍無法精確滿足比例。

其他注意事項：

- 0.35／0.48 是原計畫新提出的 profile 常數，本輪沒有跨車 FH6 證據。它們除了改變分配，也改變總量。例如相同滑桿與 50:50 配重時，現行 Mixed／Cross 的區間比例是 0.325／0.425，而新 A 是 0.35／0.48。
- 更硬的 Cross-Country 起點不代表已證明更好的落地吸收；需一起觀察壓縮行程、反彈、接地與車高。
- `DangerSign` 與 Rally 共用 match 區塊，但原計畫只要求兩種 Rally；實作應明確分支，避免順手改變 DangerSign。
- 驗收應涵蓋前重、後重、50:50、非對稱範圍與飽和；不得使用「所有車前彈簧必大於後彈簧」的通用斷言。Focus WRC 必須先取得有來源的實際範圍，不能只依車名填測試。

## 6. 本機分支開發順序與影響面

建議在已建立分支按以下順序進行，每一步維持可獨立比較的輸出。以下是實作工作清單，尚未執行。

1. **固定現況與版本邊界**：保留目前 fixture／歷史輸出，建立新 chassis 模型的明確版本與來源；決定歷史驗證如何選擇舊 owner。
2. **修好安全輸出與空力語意**：窄區間／鎖定區間優先合法值；依 2.5 實作兩軸皆未填、單軸＋必填空力平衡、雙軸已填的三條路徑。同步 Rust 型別、profile defaults／normalize、Step 1、草稿與快照的明確輸入來源，停止把未輸入描述成已估計下壓力。缺少新語意的舊草稿以未知來源處理，避免將舊 Auto=0／預設 balance=0.5 當成玩家明確輸入。
3. **導入 Road R3 修正版**：保留 FWD、ARB、車高與差速策略；驗證 FWD 阻尼連動。顯式空力係數獨立列為後續校準項。
4. **獨立導入 Rally A 候選**：加入分配與飽和判定，保持 DangerSign 行為，避免同一次 A/B 變更多種底盤參數。
5. **實機比較後再評估 R1／R2**：不把本次算術結果當成操控或圈速改善證據。

### 歷史建議的相容性不能省略

[evidence.rs::verify_recommendation](../../backend-rust/src/tuning/evidence.rs) 會呼叫 `calculate_qualified_version` 重新計算，並與已保存 recommendation 比對。當前 legacy 分流主要選擇舊 Road 齒比，chassis 仍無條件呼叫同一個 owner。因此直接改共享 chassis 有使舊 recommendation 驗證失敗的風險；這是由現行呼叫鏈推得的風險，本輪未變更公式去製造歷史失配。

需要區分 schema 格式版本與公式版本；ICE、EV、mechanical preview 均可能含底盤結果。不能只替齒比版本加字串。現有 `tuning_golden_fixtures.json`、`mechanical_desktop_v162.json` 與 TS characterization 不應再次為新公式改寫預期值；新增有來源的新基準與舊版重播契約。

| 範圍 | 預期檔案／驗收 |
| --- | --- |
| 數值與模型 | `backend-rust/src/tuning/chassis.rs`、`types.rs`；可選前後下壓力、明確空力平衡、反推公式、有限值與上下限 |
